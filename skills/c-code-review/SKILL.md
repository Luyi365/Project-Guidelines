# C 语言代码风格审查

## 用途

对照 `./references/c-style.md` 中的 C 代码规范（C-CodeStyle 精简版），对 C 语言源码进行系统化的风格审查，并输出分级审查报告。规范是唯一审查基准，不额外发明规则。

## 何时使用

- 用户要求审查 / 检查 / 评估 C 代码风格
- 用户提交、粘贴或打开 `.c` / `.h` / `.inc` 代码，希望核对是否符合规范
- 代码评审（Code Review）中需要检查风格合规性
- 用户提到 C 命名（变量/函数/结构体/宏）、缩进、注释、错误处理等关键词

## 审查流程

### 1. 确定审查范围

- 明确要审查的文件或代码片段（`.c` / `.h` / `.inc`）
- 如果用户未指定范围，默认审查当前活动文件；文件较多时可让用户确认范围

### 2. 加载规范

- 以 `./references/c-style.md` 为唯一审查基准
- 注意：规范文档中 `//: 变量` 这类注释是示例说明，不是实际代码
- 格式化可使用 [`.clang-format`](./assets/.clang-format)：将该文件复制到目标项目根目录后由 clang-format 发现并执行
- 此配置仅处理可机械化的格式规则；`while(1)`、`switch`、`inline` 与元方法的特例大括号位置，以及命名和文件顺序，仍以规范审查为准

### 3. 按类别逐项审查

对照规范逐项检查；仅对当前代码中适用的类别给出「通过 / 警告 / 违规」判定。代码未涉及的类别标记为「不适用」，不将其计入「全部通过」。

- **变量命名**：全小写下划线；「名词/形容词 + 名词」结构；静态/常量/全局/指针等类型的写法
- **结构体 / 联合体 / 枚举**：帕斯卡命名；仅源文件内部使用则纯 `struct` 形式，对外暴露则在头文件前置声明 `typedef` 类型；`typedef` 新类型后缀 `_t`；枚举成员前缀加 `结构体名_`；业内惯例缩写词用全大写（如 `ID`）
- **函数命名**：全小写下划线；「标识 + 动词 + 名词 +（子名词）」结构；`static` / `inline` 的写法；句柄注册接口函数使用 `_id_` 前缀且只能为 `static`，寄存器操作函数使用 `_id_` 前缀，汇编转 C 操作函数使用 `__asm_` 前缀
- **宏命名**：全大写下划线；普通功能宏不用下划线前后缀；头文件保护宏约定为「文件名_H」形式（如 `USER_INFO_H`）；构建预处理、汇编转C等实现类别宏用语义化前缀（如 `PRE_`、`ASM_`）区分；`_`/`__` 前缀属编译器保留区，禁止用户自定义
- **缩进**：4 空格为单位，严禁 tab；`if/else`、`switch/case`、`for`、`while`（`while()` 同行 `{`，`while(1)` 换行 `{`）、`do-while` 的标准格式；函数体大括号按特性区分（普通函数换行 `{`，`inline`/句柄注册接口函数同行 `{`）
- **注释**：主推 `/** ... */` 块式 Doxygen（文件头与函数头注释，.h/.c 统一）、`/// ...`（可选的单行便捷形式）、`/* ... */`（通用）、`// ...`（过程单行与成员注释）、`///< ...`（行尾简短注释）
- **缩写**：按三级强度审查——不缩写（保留全称：全局变量/函数名/结构体成员名/宏名）、截断式缩写（约定俗成：函数形参名/业内惯例/结构体名）、首字母缩写（取首字母：局部变量/宏参数名）
- **文件与函数顺序**：`.h` 与 `.c` 分别遵循依赖优先的文件分层规则；对外函数按生命周期与操作流程排列（创建/初始化到停止/关闭/销毁），文件私有静态辅助函数置后；状态机或硬件时序要求优先
- **其他**：`.inc` 模板文件、长语句逻辑判断符置前、逻辑返回值（1 真 / 0 假）、错误处理返回值（0 成功 / !0 错误）

### 4. 输出分级审查报告

按以下格式逐条输出，每条包含**位置**与**修改建议**：

- 🔴 **违规**：明确违反规范，需要修复
- 🟡 **警告**：建议改进，规范适用性存疑
- 🟢 **通过**：符合规范

报告末尾给出总体结论与「优先修复清单」。建议使用以下模板：

```markdown
## C 代码风格审查报告：`<文件名>`

### 🔴 违规
- `行号` — 问题描述（依据：规范原文）
  建议：<修改建议>

### 🟡 警告
- `行号` — 问题描述
  建议：<修改建议>

### 🟢 通过
- 变量命名 ✅ 结构体命名 ✅ 缩进 ✅ …

### 不适用
- 宏命名、文件顺序：当前代码片段未涉及

### 总体结论
<总结性结论>

### 优先修复清单
1. <最优先修复项>
2. …
```

### 5. 可选：给出修复示例

对违规项给出符合规范的重写示例；除非用户明确要求，否则**不直接改动用户的文件**。

## 注意事项

- 规范是「精简版」：不要要求超出规范之外的内容
- 对规范未明确覆盖的写法，标记为 🟡 **警告**并注明「规范未覆盖」，不强行判定违规
- 若同一文件无违规，明确给出「全部通过」的结论
- 审查结论应引用规范原文作为依据
